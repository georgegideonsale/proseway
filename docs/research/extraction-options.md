# PDF extraction options for Proseway

Checked 2026-11-21. Versions, release dates and wheel sizes come from the PyPI JSON API; stars and last push come from the GitHub API on that date. Speed figures are **published** numbers, mostly from vendors, measured on hardware unlike the target (i7-1165G7, 4C/8T, 7.6 GB RAM, no GPU). Treat them as rough rankings only. The lead engineer will benchmark.

Legend: **OK** = permissive, safe to depend on from Apache-2.0. **RESTRICTED** = has terms beyond OSI licences (revenue caps, field-of-use limits, non-commercial clauses). **COPYLEFT** = AGPL/GPL.

## 1. Text-layer libraries (no ML)

These give characters, spans and positions. Proseway would supply its own structure heuristics: running header/footer removal by repetition across pages, heading levels from font size and weight, column split from x-clustering, de-hyphenation, and footnote detection from small font near the page bottom.

## 4. Fit against Proseway's needs

| Need | Text-layer + heuristics (pypdfium2) | Docling | Notes |
|---|---|---|---|
| Chapters / headings | font size and weight, PDF outline via pypdf/pypdfium2 | section-header + title classes | PDF bookmarks are the most reliable chapter source when present |
| Running headers/footers, page numbers | repetition across pages + position | page-header / page-footer classes | heuristics work well on books (consistent layout) |
| Multi-column / reading order | x-clustering, needs care | built-in reading-order model | the main risk area for heuristics |
| Footnotes | small font near page bottom + marker matching | footnote class | linking the note to its call needs custom code in both |
| Tables | weak (pdfplumber rule finder at best) | TableFormer | |
| Figures + captions | images via pypdfium2 + nearest "Figure N" text | picture + caption classes | |
| Equations | none | formula class (LaTeX only with CodeFormula enrichment, slow) | |
| Code blocks | monospace font detection | code class | |
| De-hyphenation | own logic in both | own logic in both | |
| Page number per block | yes | yes (provenance per item) | |
| Scans | needs OCR engine | needs OCR engine (RapidOCR plug-in) | |

## 5. Recommendation

- **Light default engine: pypdfium2** (Apache-2.0/BSD-3, ~5 MB, no models, fastest permissive option) with Proseway's own structure heuristics. Use **pypdf** for outline/page labels. Keep **pdfplumber/pdfminer.six** (MIT) only as a debugging/fallback path, because the py-pdf benchmark shows them 35–55x slower.
- **Optional high-accuracy extra: Docling** as `proseway[docling]`. MIT code, Apache-2.0 / CDLA-Permissive-2.0 weights, explicit footnote, page-header and caption classes, and per-item page provenance. Cost: torch CPU (~127 MB wheel on Windows, CPU index needed on Linux) plus ~320 MB models. My unverified estimate for a 4-core laptop is about 1–3 s/page with OCR off, so a 300-page book would take 5–15 min. The paper measured 3.1 s/page on 8 vCPU with OCR on. Disable table and formula enrichment by default.
- **Optional OCR engine: RapidOCR + onnxruntime** as `proseway[ocr]`. Apache-2.0 code and models, pure pip, no torch, and the same engine Docling uses by default. Support system Tesseract (via `pytesseract`) as an opt-in alternative, but never require or bundle Ghostscript/OCRmyPDF.
- **Do not use:** PyMuPDF/pymupdf4llm (AGPL), marker/surya/indra (weights restricted and they forbid competing products), MinerU (custom terms; the 2509 VLM is AGPL), Nougat (CC-BY-NC, unmaintained), olmOCR (GPU only), GROBID (Java service, built for articles).
- **Benchmark these three:** (1) pypdfium2 + heuristics against a pdfplumber baseline, (2) Docling CPU standard pipeline with OCR off and the fast TableFormer, (3) RapidOCR on scanned pages (standalone and as Docling's OCR). Measure s/page, peak RSS within 7.6 GB, and header/footer, footnote and reading-order accuracy on 5–10 real books, including two-column and scanned ones.
